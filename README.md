# Explainable Cybersecurity Learning Assistant

An interactive knowledge-graph tool for exploring cybersecurity concepts — attacks, vulnerabilities, defences, tools, and how they connect. Every answer the app gives is generated by **pure graph traversal and template-based text generation** — there is no LLM or AI anywhere in the reasoning path. Every explanation can be traced back to a real edge in the graph.

## Setup (Windows)

### 1. Prerequisites

Confirm these are installed:
```powershell
python --version   # 3.11.9
node --version     # v24.14.1
```
Plus **Neo4j Desktop**, with a local DBMS running Neo4j **5.26.19**.

### 2. Backend

```powershell
cd cyber-kg-assistant\backend
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

If PowerShell blocks the activation script:
```powershell
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
```

Create `backend/.env`:
```
NEO4J_URI=bolt://127.0.0.1:7687
NEO4J_USER=neo4j
NEO4J_PASSWORD=your_password_here
```
**Important:** use `bolt://127.0.0.1:7687`, not `neo4j://localhost:7687` — the latter adds a consistent multi-second delay per request against a single-instance Community Edition database (routing-discovery overhead that doesn't apply here).

### 3. Load the graph

In Neo4j Browser, wipe any existing data:
```cypher
MATCH (n) DETACH DELETE n;
```
Then paste the entire contents of `backend/seed_graph.cypher` and run it as one single query (it's written as one continuous statement — don't split it across multiple runs, or variable references between `MERGE` clauses will break).

Verify:
```cypher
MATCH (n) RETURN count(n) AS totalNodes;        // expect 26
MATCH ()-[r]->() RETURN count(r) AS totalRels;  // expect ~48
```

### 4. Run the backend

```powershell
uvicorn main:app --reload
```
Look for `✅ Connected to Neo4j successfully.` Visit `http://127.0.0.1:8000/docs` to confirm the API is live.

### 5. Frontend

```powershell
cd ..\frontend
npm install
npm run dev
```
Visit `http://localhost:5173`. Keep the backend running in a separate terminal.

## Extending the Graph

To add new nodes/relationships:

1. Open `backend/seed_graph.cypher`
2. Add new `MERGE` statements following the existing pattern — group by node type, give every node a `name` and `description`, then add relationship `MERGE`s at the end of that block
3. **Keep it as one continuous statement** — do not add semicolons between blocks. Cypher variable scope breaks across semicolon-separated statements, which silently created duplicate blank nodes the one time this was tried (see `TESTING.md` pitfall #2)
4. Reload: wipe the DB, paste the *entire* updated script, run it once
5. Since `MERGE` is idempotent, re-running the full script is always safe — existing nodes won't be duplicated

**At larger scale (100+ nodes):** hand-writing Cypher gets error-prone. Consider authoring new nodes in a spreadsheet (one sheet per label: `Attack`, `Defence`, etc., with `name`/`description` columns, plus a separate sheet for relationships as `source, relationship_type, target` rows), then writing a small script to generate the `MERGE` statements from that spreadsheet. This isn't built yet — a natural next step if you grow the graph significantly.

Only 7 node labels and 7 relationship types are used throughout the whole system (`Attack`, `Vulnerability`, `Defence`, `Tool`, `Concept`, `Technology`, `Asset`; `EXPLOITS`, `MITIGATES`, `TOOL_USED_FOR`, `TARGETS`, `RELATED_TO`, `LEARN_NEXT`, `PREREQUISITE`) — don't introduce a new label or relationship type without updating `nodeColors.js` (for the new label's color) and, if it's a new relationship type, `explanation_engine.py`'s `RELATIONSHIP_TEMPLATES` dict (otherwise it'll fall back to a generic, less natural-sounding phrase).

## Adding New Premade Questions

Open `backend/questions.py` and add an entry:

```python
"q6": {
    "text": "How does XSS lead to session hijacking?",
    "start": "Cross-Site Scripting",
    "end": "Session Cookie",
},
```

That's it — no other code changes needed. The dropdown, the shortest-path lookup, and the explanation generation all read from this dict automatically. `start` and `end` must exactly match real node names in the graph (case-sensitive, since this bypasses `/search`).

## Core Design Principle (please preserve)

Every explanation in this app is generated by:
1. A real Cypher query against the graph (`shortestPath`, relationship pattern matches, etc.)
2. A fixed dictionary mapping relationship types to phrase templates (`explanation_engine.py`)
3. Plain Python string formatting — no model, no inference, nothing probabilistic

This is the project's defining characteristic: **every sentence the user sees can be traced back to a specific edge in the graph.** Any future feature (free-text questions, graph expansion, etc.) should preserve this — parsing a user's typed question into graph queries via keyword/entity matching is fine; generating the *answer text* via an LLM is not, without a deliberate, explicit decision to change the project's premise.
