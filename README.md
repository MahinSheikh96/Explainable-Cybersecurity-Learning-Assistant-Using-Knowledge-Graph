# Explainable Cybersecurity Learning Assistant

An interactive knowledge-graph tool for exploring cybersecurity concepts — attacks, vulnerabilities, defences, tools, and how they connect — across six domains: web application security, network security, malware and endpoint security, cloud and identity security, cryptography, and social engineering.

Every answer the app gives is generated by **pure graph traversal and template-based text generation** — there is no LLM or AI anywhere in the reasoning path. Every explanation can be traced back to a real edge in the graph. The graph itself is source-grounded: every Attack node is tied to a real MITRE ATT&CK technique ID where one genuinely exists, every Vulnerability node is tied to a real CWE entry, and web-application content is additionally grounded in the OWASP Top 10:2025. Where no genuine mapping exists (e.g. "Trojan" or "Worm," which are informal malware categories, not technique IDs), the node's description says so explicitly rather than inventing one.

**Current graph size: 185 nodes, ~330 relationships.**

## Setup (Windows)

### 1. Prerequisites

Confirm these are installed:
```powershell
python --version   # 3.11.9
node --version     # v24.14.1
```
Plus **Neo4j Desktop**, with a local DBMS running Neo4j **5.26.19**.

### 2. Backend

```powershell
cd cyber-kg-assistant\backend
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

If PowerShell blocks the activation script:
```powershell
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
```

Create `backend/.env`:
```
NEO4J_URI=bolt://127.0.0.1:7687
NEO4J_USER=neo4j
NEO4J_PASSWORD=your_password_here
```
**Important:** use `bolt://127.0.0.1:7687`, not `neo4j://localhost:7687` — the latter adds a consistent multi-second delay per request against a single-instance Community Edition database (routing-discovery overhead that doesn't apply here).

### 3. Load the graph

In Neo4j Browser, wipe any existing data:
```cypher
MATCH (n) DETACH DELETE n;
```

Then run each of the following files **in order**, pasting each one's *entire* contents as a single continuous statement (do not split any individual file across multiple runs — variable scope breaks across semicolon-separated statements within a file):

1. `seed_graph.cypher`
2. `seed_graph_batch1_webapp.cypher`
3. `seed_graph_batch2_network.cypher`
4. `seed_graph_batch3_malware.cypher`
5. `seed_graph_batch4_cloud_identity.cypher`
6. `seed_graph_batch5_cryptography.cypher`
7. `seed_graph_batch6_social_engineering_physical.cypher`
8. `seed_graph_enrichment.cypher`
9. `seed_graph_fix1_csrf_cwe352.cypher`

Every file after the original seed is written as `MATCH` (against nodes it depends on) + `MERGE` (for what it adds), so re-running any or all of them is always safe — nothing gets duplicated or overwritten.

Verify:
```cypher
MATCH (n) RETURN count(n) AS totalNodes;        // expect 185
MATCH ()-[r]->() RETURN count(r) AS totalRels;  // expect 330 (approx.)
```

### 4. Run the backend

```powershell
uvicorn main:app --reload
```
Look for `✅ Connected to Neo4j successfully.` Visit `http://127.0.0.1:8000/docs` to confirm the API is live.

### 5. Frontend

```powershell
cd ..\frontend
npm install
npm run dev
```
Visit `http://localhost:5173`. Keep the backend running in a separate terminal.

## Features

- **Guided Mode** — starts from a fixed root ("Cybersecurity") and expands outward as you click; positions new nodes in an arc anchored to the clicked node.
- **Free-Flow Mode** — blank canvas, live debounced case-insensitive search; drop any node by name and expand it manually.
- **Path Finder** — shortest path between any two nodes in the graph, with a generated explanation, generalizing beyond the fixed premade-question list.
- **Premade Questions** — 5 curated question/answer pairs with a Concise/Detailed explanation toggle.
- **Defense & Tool panels** — on any Attack node, dedicated panels surface what mitigates it (`MITIGATES`) and what tools test for it (`TOOL_USED_FOR`), pulled from live `/defenses` and `/tools` queries.
- **Dark / light theme toggle** — persisted across sessions; re-synchronizes the graph engine's color scheme on toggle.

## Extending the Graph

To add a new domain batch, follow the same pattern used by `seed_graph_batch1_webapp.cypher` through `seed_graph_batch6_social_engineering_physical.cypher`:

1. **Source before writing.** For each new Attack node, look up its real MITRE ATT&CK technique ID rather than generalizing from memory. For each new Vulnerability node, look up its real CWE ID and official title. If no genuine mapping exists for a concept (as with informal malware categories like "Trojan"), say so explicitly in the node's description — never invent a fictitious ID to fill the gap.
2. **`MATCH` what you depend on, `MERGE` what you add.** Start the batch by `MATCH`-ing any existing nodes your new content will link to (never `MERGE` them — if a dependency doesn't exist yet, the batch should fail loudly, not silently create a duplicate). Then `MERGE` every new node and relationship.
3. **Keep it as one continuous statement** — do not add semicolons between blocks. Cypher variable scope breaks across semicolon-separated statements, which silently created duplicate blank nodes the one time this was tried (see `TESTING.md` pitfall #2). The one exception: a plain `MATCH...SET` block (used for updating existing node descriptions, as in `seed_graph_enrichment.cypher`) needs an explicit `WITH *` between a `SET` and the next `MATCH` — `MERGE`'s combined read/write semantics let it chain freely without this, but bare `MATCH` does not.
4. **Link across domains where a real attack chain justifies it.** New nodes shouldn't only connect within their own batch — e.g. Cloud Metadata API Credential Theft (Batch 4) links back to the existing Server-Side Request Forgery node (Batch 1), reflecting a real, documented attack chain.
5. Reload: wipe the DB, run the original seed, then every batch file in order, then run your new file last.
6. Since every batch is `MATCH` + `MERGE`, re-running the full sequence is always safe — nothing gets duplicated.

**At larger scale (300+ nodes):** hand-writing Cypher gets error-prone. Consider authoring new nodes in a spreadsheet (one sheet per label: `Attack`, `Defence`, etc., with `name`/`description` columns, plus a separate sheet for relationships as `source, relationship_type, target` rows), then writing a small script to generate the `MERGE` statements from that spreadsheet. This isn't built yet — a natural next step if you grow the graph significantly.

Only 7 node labels and 7 relationship types are used throughout the whole system (`Attack`, `Vulnerability`, `Defence`, `Tool`, `Concept`, `Technology`, `Asset`; `EXPLOITS`, `MITIGATES`, `TOOL_USED_FOR`, `TARGETS`, `RELATED_TO`, `LEARN_NEXT`, `PREREQUISITE`) — don't introduce a new label or relationship type without updating `nodeColors.js` (for the new label's color) and, if it's a new relationship type, `explanation_engine.py`'s `RELATIONSHIP_TEMPLATES` dict (otherwise it'll fall back to a generic, less natural-sounding phrase).

## Adding New Premade Questions

Open `backend/questions.py` and add an entry:

```python
"q6": {
    "text": "How does XSS lead to session hijacking?",
    "start": "Cross-Site Scripting",
    "end": "Session Cookie",
},
```

That's it — no other code changes needed. The dropdown, the shortest-path lookup, and the explanation generation all read from this dict automatically. `start` and `end` must exactly match real node names in the graph (case-sensitive, since this bypasses `/search`).

## Core Design Principle (please preserve)

Every explanation in this app is generated by:
1. A real Cypher query against the graph (`shortestPath`, relationship pattern matches, etc.)
2. A fixed dictionary mapping relationship types to phrase templates (`explanation_engine.py`)
3. Plain Python string formatting — no model, no inference, nothing probabilistic

This is the project's defining characteristic: **every sentence the user sees can be traced back to a specific edge in the graph.** Any future feature (free-text questions, graph expansion, etc.) should preserve this — parsing a user's typed question into graph queries via keyword/entity matching is fine; generating the *answer text* via an LLM is not, without a deliberate, explicit decision to change the project's premise.

## Known Limitations

Stated explicitly rather than left implicit:

- **No formal user study has been conducted.** The system has been validated for functional correctness (33 passing automated tests), not for pedagogical effectiveness, usability, or comprehension outcomes relative to any baseline.
- **No free-typed natural-language question support yet.** Premade Questions and Path Finder require selecting or searching for concepts by name. A planned extension is a rule-based (still non-AI) keyword/entity-matching front end — not a generative model.
- **Graph coverage is broad but not exhaustive.** 185 nodes across six domains is a curated subset of the cybersecurity domain, not a complete one.
- **Relationship direction isn't always shown visually.** For architectural reasons related to how neighboring nodes are queried, some relationships render without directional arrows in the interactive graph, even though the underlying data is directional. Generated explanations are unaffected, since they're derived from the directional data itself — but reading direction off the visual graph alone isn't always reliable.
